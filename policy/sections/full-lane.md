## Full lane workflow
1. **Evidence.** The main session runs scouts with narrow questions, starting paths, an Output line, and a Skills line (usually none; a project-conventions skill when scouts must recognize framework-specific patterns). Run scouts in parallel when the questions are independent. Use `scout-haiku-low` for locating, `scout-haiku-med` for reading and summarizing (including read-only `gh`/API queries, CI logs and live endpoint checks), and `scout-sonnet-high` only when the root cause is unclear or spans modules.
   - Ask for plan-ready evidence: for every file the change will likely touch, the path, the line ranges and the exact excerpt of the relevant functions, types or config entries; the callers and tests involved; and the verification commands that exist. The planner builds on this without re-reading the files, so a scout question that only asks for counts or a summary is too thin.
   - Wait for every scout before dispatching the planner.
2. **Plan.** The main session chooses a planner tier and passes it the problem, not a solution: the user's request in their own words, what was observed, the paths of all scout output files, the user's explicit decisions and constraints, the skills inventory file path, an Output line with the plan path, and a Skills line for the planner itself (for example, an architecture or domain skill that shapes the plan).
   - Never prescribe the approach, the task split or the tiers. The main session is not at the planner's reasoning level; an idea of its own goes in labeled as an unverified hypothesis, and the planner decides the plan.
   - One planner instance per topic: the plan it wrote and the tasks directly related to it. Resume an instance only for its own plan (NEED_EVIDENCE answers, REPLANs of its tasks). A new topic that needs design (a new feature, an unrelated bug, a large finding outside that plan) gets a fresh planner and its own new plan file; small, clear work goes to the fast lane. Never grow one plan file with unrelated topics.
   - If the planner returns OUT_OF_TOPIC or NO_PLAN_NEEDED, follow it: start a fresh planner for the new topic, or write a fast-lane spec.
   - If the planner returns NEED_EVIDENCE, dispatch one scout per `## Scout <k>` section of its requests file, passing the file path and the section; then resume the same planner instance with the scouts' output paths through SendMessage.
   - The planner treats the evidence files it is given as verified and has an evidence budget: at most {{planner_evidence_budget}} Read/Grep/Glob calls in total, each to fill a gap it names in the plan. A larger gap goes back as NEED_EVIDENCE, answered by cheap scouts, instead of the planner investigating on its own. Reading the files its delegation names, the project rules files and the listed SKILL.md files does not count against the budget.
   - Allow at most {{max_evidence_rounds}} evidence rounds. After that, the planner must plan with what it has and list its assumptions explicitly.
3. **Execute.** Dispatch each task to the start tier the plan assigns; the plan's executor tier is the fallback. For a plan without start tiers, start on its executor tier if that is a Haiku tier, otherwise on `exec-haiku-high`; ask the user first about a task with more than {{skill_cap_haiku}} skills. Pass the plan file path, the task ID, the task's executor Skills line and Project rules line exactly as written in the plan, and an Output line. Never pass a paraphrase of the task. Order and branch tasks as Task contracts says.
4. **Gate.** For every finished task, run `{{plugin_name}}-gate <plan path> <task-id> <worktree path> --commits <shas from the status line> --report <report path> --out <gate file> --base <integration branch>` once from the main checkout (see Gate). It prints `PASS <gate file>` or `FAIL <gate file> checks=<names>`; never repeat its checks by hand. Exit 2 is a usage or plan error (see Gate).
5. **Verifiers, only when triggered.** A per-task verifier (the plan's verifier tier for the tier that did the work) runs before the task merges when the plan marked it `Verify: task`, or when a gate check other than Green failed (red, integrity, coverage, scope, contract, or report mismatch); these failures need judgment, not a blind retry. Other triggered tasks go to the plan's batch: `Verify: batch`; a task that ran below the plan's executor tier, even if the plan marked it Verify: no; a task after a FIX round or an escalation; a task calibration sampling selected. When every task has passed its gate and merged into the integration branch, split the batch in plan order into groups of at most {{batch_verify_max_tasks}} tasks whose verifier Skills lines together name at most {{skill_cap_other}} skills, and dispatch one verifier per group, in parallel, at the strongest verifier tier its tasks need; it checks and fixes each task in that task's kept worktree (see Gate). An older plan's `Verify: yes` counts as `Verify: task`.
   Pass the plan path, task ID, branch or worktree, the executor's report path, an Output line, the gate results file path, and the task's verifier Skills line and Project rules line exactly as written in the plan; a batch verifier gets every task ID with its report and gate file paths, each task's worktree path, and the union of the Skills and Project rules lines.
6. **Act on the result.**
   - Gate passed and no verifier is due, or its verifier returned PASS (in a batch verdict, `<task-id>:PASS`): the task is done.
   - Only the Green check failed (`checks=green`): resume the same executor instance through SendMessage with the gate file path. This counts as a FIX round. No verifier is needed for it.
   - Verifier FIXED: the verdict is final; no verifier checks the task again. Gate it again with `--report <verdict file>` and `--commits` from the status line (for a batch task, all its commits since the base in its first gate file, with `--base` that sha). On PASS the task is done (merge a batch task again); on FAIL, resume the same verifier instance with the gate file path (a verifier round).
   - Allow at most {{max_fix_rounds_per_tier}} FIX rounds per executor tier, and {{max_fix_rounds_per_tier}} verifier rounds per task. After an executor's last FIX round, escalate the executor: from a start tier below the plan's executor tier straight to that tier, otherwise one tier up. Launch a fresh executor with the plan path, the task ID, the Skills line and Project rules line as written in the plan, the paths of the earlier verdict and failure files, and a new Output line. After a fallback, a verifier for the new work is a fresh instance of the plan's fallback verifier tier. After the last verifier round, handle the task as a REPLAN with the verdict and gate file paths.
   - REPLAN, when the plan's design is wrong: resume the same planner instance with the verdict file path, so it can revise that task in the plan file (editing only that task), including its skills if the problem was a skill conflict or a missing skill. The planner may consult the advisor once for this revision (Advisor rules). After the revision, re-execute the task. If a second REPLAN occurs for the same task, move up one planner tier. A REPLAN with `fix=small` goes to the fast lane instead: its executor gets the verdict path as the spec input; log it as a deviation.
   - BLOCKED: the status line's `reason=` says why; fix the environment issue if that reason shows it is clearly mechanical. Otherwise, treat it as a failure under the escalation caps.
7. **Final gate and integrate.**
   - Merge only when every task has passed its gate (and its per-task or batch verifier, if one ran) and the full test suite passes on the integrated branch. Then commit with a clear message and merge. Where a project forbids red-only commits on its main branch, fold the red commit into its green commit after the gate and before the merge.
   - Never force-push or rewrite shared history.
   - Resolve trivial merge conflicts directly. Route non-trivial conflicts as a new task to `exec-sonnet-high`, with verification.
   - Destructive database migrations, data deletion, and production deploys are outside auto-merge scope: prepare them fully, then report.
   - Wrap-up (every task has passed: final gate, merge, docs, log, report) never spawns or resumes a planner. The main session writes the log; docs edits go to the fast lane. A problem found now is either small and clear (fast lane) or a new topic for a fresh planner.
8. **Log** every delegation, as described under Logging.
