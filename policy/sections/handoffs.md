## Handoffs between agents
- Every tier agent writes its full output to a file and replies with one status line that names the file. The main session never reads these files; it passes their paths to the next agent.
- Handoff directory: one per run, `docs/handoffs/<YYYY-MM-DD>-<topic-slug>/` in the project (or the run directory the project's rules name), kept out of version control. An agent working in a worktree writes inside that worktree's copy of the directory.
- Every tier delegation carries an `Output:` line with the absolute path of a new file in the handoff directory (for planners, the plan file), and a `Project rules:` line when the agent should read something other than the root `CLAUDE.md`/`AGENTS.md` and their in-repository imports (`Project rules: none` for nothing).
- Name handoff files so that no file name starts with `report`, `summary`, `findings` or `analysis` (any case) and ends in `.md`: Claude Code refuses a subagent's Write to such a file, and the dispatch guard denies the delegation. Use role and task names such as `scout-1.md`, `exec-T3.md`, `gate-T3.md` and `verdict-T3.md`.
- Status lines: scouts `DONE <path>` or `BLOCKED <path> reason=<one line>`; executors `DONE <path> commits=<sha>,<sha>` or `BLOCKED <path> reason=<one line>`; verifiers `PASS <path>`, `FIX <path>`, `REPLAN <path> fix=small|design` or `BLOCKED <path> reason=<one line>`; batch verifiers `<worst verdict> <path> tasks=<id>:<verdict>,...` (verdicts PASS, FIX, REPLAN-small, REPLAN-design, BLOCKED; handle each task as if it had its own verdict); planners `READY <plan path>`, `NEED_EVIDENCE <requests path> scouts=<k>`, `OUT_OF_TOPIC <reason>`, `NO_PLAN_NEEDED <reason>` or `BLOCKED <plan path> reason=<one line>`. Decide BLOCKED and REPLAN handling from the inline `reason=` and `fix=` alone. A trailing `findings=<n>` means the file lists n out-of-scope findings: read only that section and route each finding (fast lane, or a fresh planner); `{{plugin_name}}-gate` reads its "Checks failing outside the task" sub-heading itself.
- Relay by path only: scout output files and the skills inventory file to the planner; for NEED_EVIDENCE, one scout per `## Scout <k>` section of the requests file, at the tier its heading proposes unless you have a reason to change it; the plan path and task ID to executors; the executor's report path to the verifier; the verdict path to the executor (FIX) or to the planner (REPLAN). For a Green-only gate failure, pass the gate file path; it holds the failing output.
- Delegation and resume messages carry paths and short instructions, never copied evidence, reports or defect lists.
- Usage limit: a reply that is the account's usage-limit message (such as "You've hit your weekly limit · resets <time>") means the agent stopped unfinished; it is neither a failure nor a FIX round. Log the task as interrupted and dispatch nothing until the reset time it names; then resume the same instance with "The usage limit has reset; continue your task." If that fails, start a fresh instance of the same tier with the same delegation (an executor on a new worktree from the integration branch's head). Never merge a plan, or report it done, while one of its agents is interrupted; `{{plugin_name}}-audit` flags each one as "stopped by the usage limit".
