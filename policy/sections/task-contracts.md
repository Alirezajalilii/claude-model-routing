## Task contracts
Plans declare, per task, what it provides to sibling tasks, what it requires from them and which tasks it runs after (Plan Contract, Task contract format). The main session derives the run order and a gate check from these lines with `{{plugin_name}}-plan`; it never orders tasks by hand.
- **Order.** After the planner returns READY, run `{{plugin_name}}-plan waves <plan path>`. Exit 0 prints one line per wave; each task is followed by the tasks it depends on. Exit 1 prints contract errors (an unknown task, a requires line that no provides line matches, a cycle): resume the same planner instance with the path of a file holding them, to fix the Contract blocks of the tasks named. This contract fix is not a REPLAN: it does not count toward the REPLAN limits and needs no advisor consult. When the only error is `no task has a Contract line`, the plan predates contracts: order its tasks by hand. Exit 2 is a usage or file error.
- **Branches.** Before the first task, create the plan's integration branch `agent/<plan-slug>-integration` (`<plan-slug>` is the plan file name without its date and `.md`) from the base branch. A task is ready when every task it depends on has passed and been merged into the integration branch. Dispatch ready tasks in parallel, each in its own worktree branched from the integration branch's head, and merge each task into the integration branch as soon as it passes; where red-only commits are forbidden, fold the task's red commit into its green commit before that merge. The final gate runs on the integration branch; then merge it. Name each task branch `agent/<plan-slug>-<task-id>` and create its worktree on it (`git worktree add -b`); a later worktree for the same task takes `-2`, `-3`. `{{plugin_name}}-clean` finds a run's branches and worktrees only by these names, never on a detached HEAD.
- **Gate.** The Contract check runs `{{plugin_name}}-plan check <plan path> <task-id> <worktree path>` with the plan's absolute path in the main checkout (plans are not in worktrees). Exit 0: every provides and requires line of the task is present. Exit 1 lists what is missing. A missing provides line, or a requires line the task's own diff removed, fails the gate as a check other than Green. Any other missing requires line means the worktree's base lacked the provider: recreate the worktree from the integration branch's head and dispatch the task again; this is not a FIX round.
- **Failed providers.** A task does not run while a task it depends on has not passed. When that task ends BLOCKED or fails after the escalation caps, report its dependents with it; tasks that do not depend on it go on.
- Presence is not correctness: the requiring task's own tests and the full suite on the integration branch judge behavior.
